The shape of the plan

The documentation says what Agentiik is. This says in what order it becomes that, and nothing else: no dates, no estimates, no capacity. It is the one document here that is expected to be rewritten rather than amended, because an order survives being wrong in a way a schedule does not.

A milestone here is not a batch of work. It is a sentence that becomes true and does not become false again. A workflow runs to completion on one machine with no server is a milestone. The graph evaluator is written is not one, because nothing outside the code can tell whether it happened.

Each of them carries the same four things, in the same order every time: what it makes possible, why it sits where it does, the work it requires, and the fact you can check to say it is done. The work is listed in full rather than summarised, as three to six named groups per milestone, each saying which repository it lands in, and every task carrying a § link to the section of the documentation that specifies it. A task marked implied is work the documentation assumes without writing down: a fixture, a test harness, a migration.

That last column is the point of listing them this way. A plan derived from a specification can be checked against it, task by task, instead of believed. Where a task has no section to point at, either the documentation is missing a page or the task is not really needed. Both are worth finding out.

The closing fact still governs. A milestone is crossed when its sentence is true, not when every line under it is ticked, and a line that turns out not to serve the sentence is dropped rather than carried.

Why no dates

One maintainer cannot hold a calendar, and a missed date reads worse afterwards than an order does, because the order stays true at any pace while the date is simply wrong. The version numbers are markers of sequence, not promises of delivery: v0.4.0 means after v0.3.0 and before v0.5.0, and says nothing about when. They are, however, the real versions: Agentiik carries one version across every repository, so the milestone called v0.4.0 is the release tagged v0.4.0 everywhere, and this plan is a list of releases in the order they can be made rather than a numbering invented for the occasion. If dates ever become useful (because somebody else is waiting on one), they belong in milestones on the repositories, next to the issues that move, not in a document that is read months after it was written.

§

Why this order

Three rules decide the sequence. Everything else in it is negotiable.

  • The contract ships before anything that reads it. agentiik/schemas is released first and released again before each change, because it is the only cross-repository dependency for the workflow format. A format settled after the fact, by whichever code happened to consume it first, is a format the core, the console, the two applications and the workflow.language tool will each have learnt slightly differently, which is the exact failure the repository was extracted to prevent.
  • One path end to end before any width. v0.1.0 runs a whole graph on one machine before a server exists. What an envelope has to carry, what a brick actually receives, which port a rejected item leaves by: all of it is discovered by running a workflow, and discovered far more cheaply with no controller, no task bus and no runner standing around it.
  • Nothing multi-user before the permission model. Sharing, namespaces and roles land before the console, before triggers and before MCP, because each of those three is a way in. A door added before the lock never quite closes afterwards: there is always one path that worked before permissions existed, and nobody goes back to shut it.

v0.1.0: The language runs on one machine

59 done

Makes possible: agk run --local takes an agentiik.yaml, runs its graph, and hands back the output envelopes. No server, no account, no database.

This exists so that the workflow language and the brick contract meet reality before anything depends on them. What an envelope has to carry, what a brick actually receives, which port a rejected item leaves by: all of that is learnt by running a graph, and it is learnt at a tenth of the cost with no controller, no task bus and no runner standing around it. Everything after this milestone assumes these two things are settled; this is the milestone whose job is to find out that they are not.

The evaluator and the container driver are libraries here rather than internals, and that is a constraint the rest of the plan leans on: agk run --local has to be the same code path a server run takes, or it becomes a second implementation that drifts from the first. The schemas carry a description and examples on every keyword from this first release rather than from the day somebody needs them, because the language reference and workflow.language are both generated from them later.

0 of 91 done

Makes possible: the same workflow, sent to a server, executed by a runner somewhere else, and watched while it happens.

The split between controller, task bus and runner is where the documentation takes its largest bet, and where being wrong costs the most to undo later. Past v1

The documentation keeps a list of what v1 deliberately does not do, and that list is not a backlog: most of it was left out because doing it would cost more than it returns, and that is still true after v1. Three items on it are different, in that the design already leaves the door open and closing that door would be the mistake. A fourth is not on that list at all: the Helm chart, which Repositories names as later work rather than as something refused. It belongs beside them for the same reason.

What could reorder this

A plan is more useful when it says where it expects to be wrong.

  • The brick contract does not survive v0.1.0. The most likely single failure, and the cheapest place for it to happen. If running real workflows shows that the envelope has to carry something it does not, or that a per-port barrier is the wrong shape, everything after it moves. That is the milestone doing its job, not the plan failing.
  • v0.8.0 can move anywhere after v0.1.0. It depends on the brick contract and on nothing later. It is the slack in the plan, and it is deliberate.
  • v0.6.0 and v0.7.0 can swap. Whichever is done first makes the other easier to judge: the console shows what a run looks like to a person, MCP shows what it looks like to a client that cannot see. Either order works.
  • v0.5.0 before v0.4.0 does not work. A trigger has to resolve a commit. Starting runs against a moving branch is exactly the drift the hosted repository exists to prevent, and building it that way first means building it twice.
  • v0.3.0 before every surface does not move. This is the one ordering that is not up for discussion. Console, triggers and MCP are three ways in, and permissions have to exist before any of them, not alongside.
  • Somebody else starts using it. The plan assumes one maintainer and no users. A single real user reorders everything after the milestone they arrived on, because their installation cannot be broken in the way an empty one can. At that point deployment and migration notes stop being a v0.9.0 concern.
How this document changes

By rewriting, not by amending. A milestone that turns out to be two milestones becomes two; one that turns out to be unnecessary is deleted rather than marked as dropped. This is not a record of what was planned (the repositories hold that, in their commits and their releases); it is a statement of the current best order, and a statement of that kind is only worth reading if it is current.
