An order, not a schedule. Ten milestones, each one making true something the next one needs, from a workflow that runs on a laptop to four clients reading the same run.

§

The shape of the plan

The documentation says what Agentiik is. This says in what order it becomes that, and nothing else: no dates, no estimates, no capacity. It is the one document here that is expected to be rewritten rather than amended, because an order survives being wrong in a way a schedule does not.

A milestone here is not a batch of work. It is a sentence that becomes true and does not become false again. A workflow runs to completion on one machine with no server is a milestone. The graph evaluator is written is not one, because nothing outside the code can tell whether it happened.

Each of them carries four things, in the same order every time: what it makes possible, what it takes to get there, which repositories it touches, and the fact you can check to say it is done. The last is the one that matters. A milestone is crossed when its sentence is true, not when every line under it is ticked, and a line that turns out not to serve the sentence is dropped rather than carried.

Why no dates

One maintainer cannot hold a calendar, and a missed date reads worse afterwards than an order does, because the order stays true at any pace while the date is simply wrong. The version numbers are markers of sequence, not promises of delivery: v0.4 means after v0.3 and before v0.5, and says nothing about when. They are, however, the real versions: Agentiik carries one version across every repository, so the milestone called v0.4 is the release tagged v0.4.0 everywhere, and this plan is a list of releases in the order they can be made rather than a numbering invented for the occasion. If dates ever become useful — because somebody else is waiting on one — they belong in milestones on the repositories, next to the issues that move, not in a document that is read months after it was written.

§

Why this order

Three rules decide the sequence. Everything else in it is negotiable.

  • The contract ships before anything that reads it. agentiik/schemas is released first and released again before each change, because it is the only cross-repository dependency for the workflow format. A format settled after the fact, by whichever code happened to consume it first, is a format the core, the console, the two applications and the workflow.language tool will each have learnt slightly differently — which is the exact failure the repository was extracted to prevent.
  • One path end to end before any width. v0.1 runs a whole graph on one machine before a server exists. What an envelope has to carry, what a brick actually receives, which port a rejected item leaves by: all of it is discovered by running a workflow, and discovered far more cheaply with no controller, no task bus and no runner standing around it.
  • Nothing multi-user before the permission model. Sharing, namespaces and roles land before the console, before triggers and before MCP, because each of those three is a way in. A door added before the lock never quite closes afterwards: there is always one path that worked before permissions existed, and nobody goes back to shut it.

v0.1 — The language runs on one machine

Makes possible: agk run --local takes an agentiik.yaml, runs its graph, and hands back the output envelopes. No server, no account, no database.

This exists so that the workflow language and the brick contract meet reality before anything depends on them. What an envelope has to carry, what a brick actually receives, which port a rejected item leaves by — all of that is learnt by running a graph, and it is learnt at a tenth of the cost with no controller, no task bus and no runner standing around it. Everything after this milestone assumes these two things are settled; this is the milestone whose job is to find out that they are not.

  • agentiik/schemas 0.1: the workflow file, the brick manifest and the envelope, every keyword carrying its description and examples from the first release rather than from the first time somebody needs them.
  • The graph evaluator and the container driver, as importable libraries. That is not a style preference: it is the only thing that makes agk run --local the same code path as a server run instead of a second implementation that will drift.
  • Ports, needs, merge strategies, fan-out, exit codes, the size rules, and the environment the container is given.
  • agk validate and agk run --local.
  • Three or four bricks — enough that the contract is exercised rather than described.
Done when

A multi-step workflow with a fan-out and a merge runs end to end on a laptop, and running it again on the same inputs produces the same envelopes.

v0.2 — A server runs it instead

Makes possible: the same workflow, sent to a server, executed by a runner somewhere else, and watched while it happens.

The split between controller, task bus and runner is where the documentation takes its largest bet, and where being wrong costs the most to undo later. So the fact to make true here is narrow and checkable: a runner never speaks git, never holds a lasting credential, and obtains what its task names only by redeeming that task's grant. If that holds under a real run, the rest of the architecture follows; if it does not, better to know before four clients are built on it.

  • Controller, task bus, runner, and the HTTP API at /api/v1.
  • Storage: envelopes and artifacts in an object store, runs in a database.
  • Grants: presigned URLs, secret values, repository objects — everything the task names and nothing beyond it.
  • Run states, the heartbeat, and what happens to a task whose runner stops answering.
  • agk against a server, on the same evaluator it uses locally.
Done when

A runner on another machine executes a step having held nothing but its task's grant, and killing that runner mid-step leaves the run in a state it resumes from rather than one it has to be rescued from.

v0.3 — More than one person

Makes possible: two people, two namespaces, and nothing of one visible from the other except what was shared.

This comes before the console, before triggers and before MCP, and the reason is the third rule: each of those is a way in. A door added before the lock never quite closes afterwards — there is always one path that worked back when permissions did not exist, and nobody goes back to shut it. Local accounts only, authenticated by passkey; the principal model stays provider-agnostic so that federating it later touches authentication and not authorisation.

  • Principals, namespaces, and passkey authentication.
  • Permissions, roles, scopes and their resolution order.
  • Sharing, and what sharing deliberately does not expose.
  • Quotas per namespace, sessions and tokens.
Done when

A principal with no permission on a namespace cannot establish that it exists — not through the API, and not through an error that distinguishes absent from forbidden.

v0.4 — The workflow is a repository

Makes possible: a workflow is a git repository served by Agentiik, pushed to like any other, and a run resolves a commit.

This is the claim the documentation defends at greatest length: the repository is integrated, not connected. What hosting buys over a connection to a forge is precise — a version cannot drift beneath a run, an invalid workflow cannot be pushed at all, and repository access is the permission model that already exists rather than a second one to reconcile with it. That last clause is exactly why this milestone sits after v0.3 and not before it.

  • Git hosting, the default branch and its protection.
  • Refusing an invalid agentiik.yaml at the push, which is the only place the refusal is worth anything.
  • files, includes, extends and defaults, resolved in the order the documentation fixes.
  • The runner fetching the tree as content-addressed objects with the task's grant, exactly as it fetches an artifact — so the earlier claim survives the arrival of git.
  • Memoisation and replay.
Done when

Pushing an invalid workflow fails at the push. A run records the commit it resolved, and replaying it replays that commit even after the branch has moved on.

v0.5 — Runs start without being asked

Makes possible: a workflow starts on a schedule, on a webhook, or because another workflow called it.

Short, and placed here rather than earlier for one reason: a trigger resolves a commit, so it needs v0.4 to have something to resolve. A scheduled run that silently follows a moving branch is the drift the whole repository design exists to prevent.

  • Manual, scheduled and webhook triggers.
  • Signed webhooks, and the handling the documentation requires of them.
  • What a trigger puts into the context the expressions can see.
  • Sub-workflow calls, bounded by the maximum depth — the only way the graph is allowed to repeat itself.
Done when

A scheduled workflow runs with nobody present, a webhook whose signature does not verify starts nothing, and every triggered run names what triggered it and at which commit.

v0.6 — A console to watch it

Makes possible: a run is read from end to end without a command line, and a workflow is edited without leaving the browser.

The console arrives late on purpose. Everything it shows has to exist and be right already, or it becomes the place where the rules get decided — and a rule decided in an interface is a rule the API does not enforce. Built in this order it is a view of a system rather than the system itself, which is also what lets YAML stay the source of truth even while editing happens here.

  • agentiik/design: the tokens, the type roles, the icon set and the specimen sheet, extracted before two clients disagree about them rather than after.
  • The run list, the workflow and its graph, the run inspector, the repository browser.
  • The sharing panel — the one part of the console with no YAML counterpart, by design.
  • A format-preserving YAML editor, so that a change made here produces a diff a human would have written.
Done when

A failed run is diagnosed in the console alone — the step, the exit code, what was refused — and a workflow edited there comes back as YAML whose diff contains only what changed.

v0.7 — An agent can use it

Makes possible: a model-driven client discovers Agentiik, learns the language, writes a valid workflow and runs it — and a workflow itself appears to such a client as a server of tools.

MCP is native here, not a gateway bolted onto the API, and that is the part worth getting right rather than early. Two distinct servers: the platform's, and any workflow exposed as one. The second is where the discipline shows — a workflow's server exposes tools and nothing else, because a resource would quietly turn workflow:run into a read path into the repository and undo the separation the roles were built around.

  • The platform server and its tools, each one bound to the permission it already needed.
  • workflow.language, generated from schemas — which is why that repository has carried descriptions and examples since v0.1, and why its build fails without them.
  • A workflow as an MCP server: tools only, no resources, no prompts, no access to its tree.
  • Errors and obligations, so that a client is told what it did wrong in terms it can act on.
Done when

A client that has never seen Agentiik writes a valid workflow from workflow.language alone, and workflow:run on a workflow reveals nothing of its tree.

v0.8 — A catalog worth pulling from

Makes possible: somebody who did not write the engine writes a brick, in a language the project does not use, and it runs.

The brick contract has held since v0.1; this is what turns it into a catalog other people can build on. It is also the one milestone that never needed to wait — it depends on v0.1 and on nothing after it, so it can be pulled forward into any gap. That is a property worth stating, because a plan whose every item is blocked by the previous one has no room to absorb a week where the appetite is elsewhere.

  • The standard catalog, one directory per brick, built and published as one matrix.
  • Images signed, carrying the OCI annotations required of any brick, each with its SBOM — which is what lets an operator answer an advisory about a dependency without waiting for one about Agentiik.
  • agentiik/brick-sdk: the optional helpers for Go, Python and TypeScript, written so that nothing in them is ever required.
  • Catalog pages on the site, generated rather than maintained by hand.
Done when

A third-party brick, in a language the project does not use and under a licence it did not choose, runs unmodified — and its author never had to read the engine to write it.

v0.9 — Somebody else can install it

Makes possible: an installation that its author did not perform.

Everything up to here runs where it was written, which hides a great deal: every assumption about the host, every step that only works because somebody knows to do it. This is the milestone where installing stops being knowledge and becomes a document — and where the three deployment profiles either hold or are found to be two profiles and a wish.

  • Profile A, a single host. Profile B, on-premise and redundant. Profile C, AWS with managed resources.
  • The installer, installing a runner, the runner-side hooks, sizing, and what the first run does.
  • The Terraform provider, which is what turns the second installation into an apply rather than a second afternoon: namespaces, workflow repositories, grants, groups, service accounts and secret declarations, written down instead of clicked. It belongs here and not earlier because it manages what v0.3 and v0.4 defined, and there is nothing to declare before they exist.
  • Upgrade and migration notes, written against a real upgrade rather than an imagined one.
Done when

Somebody who did not write the code installs profile A and runs a workflow, following the document and asking nothing — and a second environment is an apply against the first one's configuration rather than the same afternoon again.

v1.0 — It fits in a pocket, and it holds

Makes possible: the four clients the documentation promised, on one model, and a project that knows what to do when a vulnerability arrives.

v1.0 adds no capability. It closes the scope: the mobile applications complete the set of clients, and the security work turns a written threat model into one that has been tested against the running thing. A version number is a claim about what somebody else can rely on, which is why the disclosure process has to work before the number is handed out, not after.

  • iOS and Android: the common scope, the platform choices, and what the applications deliberately do not do — authoring and offline editing are not on this list by accident.
  • Push notification delivery.
  • A security review against the threat model, the three tiers of containment included, and against what the documentation openly says it does not defend.
  • The supply chain end to end: signed images, SBOMs, advisories per component rather than per project.
  • The disclosure process live, and exercised once before it is needed.
Done when

All four clients read the same run with none of them knowing anything the others cannot, and a vulnerability report travels the whole path from private disclosure to published advisory.

Past v1

The documentation keeps a list of what v1 deliberately does not do, and that list is not a backlog: most of it was left out because doing it would cost more than it returns, and that is still true after v1. Four items on it are different, in that the design already leaves the door open and closing that door would be the mistake.

DeferredWhat v1 already did for it
External identity providers — OIDC federation, SCIM provisioningThe principal model is provider-agnostic, so adding them touches authentication and not authorisation. That is the whole reason v0.3 was built the way it was.
Kubernetes as a substrateThe container driver sits behind an executor interface. A Job or Pod executor touches neither the controller nor the language.
A Helm chartFollows the executor above, and belongs to agentiik/deploy rather than to a release of the core.
An external policy engine — OPA, CedarRoles and grants are evaluated in the API against the database. Delegating that later is a substitution, not a redesign, as long as the permission vocabulary does not grow in the meantime.

The rest of the list — field-level permissions inside an envelope, authoring on mobile, hardware-level tenant separation, long-running bricks and continuous streams, loops in the graph, a public brick marketplace — stays out. Each of them is set out with its reasoning under Out of scope for v1, and the reasoning does not expire with the version number.

What could reorder this

A plan is more useful when it says where it expects to be wrong.

  • The brick contract does not survive v0.1. The most likely single failure, and the cheapest place for it to happen. If running real workflows shows that the envelope has to carry something it does not, or that a per-port barrier is the wrong shape, everything after it moves — and that is the milestone doing its job, not the plan failing.
  • v0.8 can move anywhere after v0.1. It depends on the brick contract and on nothing later. It is the slack in the plan, and it is deliberate.
  • v0.6 and v0.7 can swap. Whichever is done first makes the other easier to judge — the console shows what a run looks like to a person, MCP shows what it looks like to a client that cannot see. Either order works.
  • v0.5 before v0.4 does not work. A trigger has to resolve a commit. Starting runs against a moving branch is exactly the drift the hosted repository exists to prevent, and building it that way first means building it twice.
  • v0.3 before every surface does not move. This is the one ordering that is not up for discussion. Console, triggers and MCP are three ways in, and permissions have to exist before any of them, not alongside.
  • Somebody else starts using it. The plan assumes one maintainer and no users. A single real user reorders everything after the milestone they arrived on, because their installation cannot be broken in the way an empty one can — and at that point deployment and migration notes stop being a v0.9 concern.
How this document changes

By rewriting, not by amending. A milestone that turns out to be two milestones becomes two; one that turns out to be unnecessary is deleted rather than marked as dropped. This is not a record of what was planned — the repositories hold that, in their commits and their releases — it is a statement of the current best order, and a statement of that kind is only worth reading if it is current.
