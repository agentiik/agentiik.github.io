A multi-user workflow engine in which every brick is an ephemeral OCI container and every workflow is a YAML file, versioned alongside the code it serves.

§

Scope

Agentiik runs workflows built from bricks. A brick is an OCI container started for the duration of one step and destroyed afterwards. A workflow is a directed acyclic graph of bricks, described entirely in YAML, whose source of truth is a file that lives in version control. One installation serves many users, who own workflows inside namespaces and share them with named roles.

What the product does

  • Describes a workflow in YAML, with file includes, block inheritance and matrices, following the syntactic model of GitLab CI.
  • Exposes several named inputs and several named outputs, at workflow level and at brick level alike.
  • Runs every brick in an ephemeral container on a fleet of runners, with resource limits and network isolation by default.
  • Carries batches of JSON items between bricks, spilling large payloads to an object store and referencing them by URI.
  • Triggers a workflow on a schedule, on a webhook, on an event, on a manual call or from another workflow.
  • Serves several users and groups on one installation, authenticated by passkey and optionally with passwords forbidden outright, with workflows owned by namespaces and shared to named principals with read, run and edit roles.
  • Replays a run from a chosen step, reusing the artifacts already produced upstream.
  • Runs a whole workflow locally, with no server, from the working tree and a Docker daemon alone.
  • Installs from the same images on one machine, on a redundant on-premise fleet or on managed cloud services, with runners added as containers or as a system service on bare metal.
  • Follows and unblocks runs from a phone: run history, live state, approval of a waiting run, and push notification on failure.
  • Speaks the Model Context Protocol on two surfaces: one to operate the platform, one that publishes a chosen workflow as a tool.

What the product does not do

  • No brick ships as code interpreted inside the engine. A brick is an image and nothing else.
  • No language-model node and no agent enters the engine or the standard catalog. Bricks are API calls and deterministic tools.
  • The engine embeds no general-purpose scripting language for conditions and templating. See Expressions.
  • No anonymous sharing. A workflow is shared to a named principal, never through a public link.
  • No workflow authoring on mobile. The phone is for watching and unblocking, not for building.

Licence

The project is published under OSI-approved licences, split by what each repository is for rather than uniformly: copyleft where the server lives, permissive everywhere a third party has to embed something. Repositories sets out the split and the reasoning.

Data exchange model

The default channel between two bricks is a batch of JSON items. That channel stays readable, diffable and replayable, but it does not suit heavy payloads. Agentiik therefore applies an automatic spill threshold to the object store.

Decision

Artifacts are content-addressed. The logical URI agk://run/<run>/<step>/<port>/<name> resolves to a physical key sha256/<digest>. Two steps producing identical bytes store one copy, and a replay that recomputes the same content writes nothing. Deduplication is scoped per namespace, so that two namespaces never share a physical object and an existence check can never reveal what another namespace holds.

How long an artifact lives

An artifact does not live forever, and how long it lives is declared rather than inherited from whatever the object store was configured to do. Two mechanisms, which answer two different questions: a duration answers how long may this be fetched, and a single fetch answers may this be fetched more than once. They compose — a one-shot artifact still has a duration, which is what expires it when nobody ever comes for it.

in agentiik.yaml
outputs:
  invoices:
    from: { step: archive, port: out }
    retain: 90d                    # available for ninety days
  payslips:
    from: { step: render, port: out }
    retain: { for: 24h, fetches: 1 }   # gone on collection, or a day later

defaults:
  retain: 7d                       # intermediate artifacts, and any output not saying otherwise

What expiry acts on

Expiry applies to the reference, never to the object. The row in artifacts binding a run, a step and a port to a digest is what is dropped; the physical sha256/<digest> object is collected once its reference count reaches zero, and not before. This falls out of content addressing and is not a detail: two runs that produced identical bytes share one object, and expiring one run's output must not reach into the other's. A one-shot artifact collected by its owner therefore leaves the same bytes perfectly readable through another run that still references them — which is the correct behaviour, and worth knowing before it is mistaken for a leak.

A single fetch

  • Only a workflow output can be one-shot. An artifact travelling between two steps cannot be, because a fan-out reads it once per shard and a replay reads it again afterwards: consumption there would mean a graph that runs correctly the first time and not the second.
  • A fetch counts when the response completes. A transfer that is interrupted, refused, or ranged over part of the object does not consume the artifact, so a client that loses its connection retries against an artifact still there.
  • The count is per artifact, not per principal. Two people sharing a namespace share the one collection, which is why fetches is written as a number rather than as a flag: fetches: 2 is what a workflow feeding two consumers declares.
  • Once consumed, the reference is gone immediately rather than at the next sweep. A later request answers 410 Gone and not 404, so that a client can tell this existed and is finished from this never existed, and the run detail keeps showing the artifact's name, size and digest with its collection recorded.

What it costs downstream

  • Replay. Replaying from a chosen step reuses the artifacts produced upstream, so a run whose artifacts have expired can be replayed only from the beginning. A run says which it is: once any input to a step it could restart from is gone, the run is marked as replayable from the start only, and the console says so where it would otherwise offer the step.
  • Memoisation. A cache entry is invalidated when an artifact it would hand back has expired. A cache hit that resolves to a collected one-shot artifact is not a hit, because the point of memoisation is to skip work whose result is still available — and a workflow that declares an output one-shot has said that its result is not.
  • The ceiling is the namespace's. retain is capped by the namespace quota and cannot exceed it; a workflow may always ask for less. An operator raising the ceiling does not extend artifacts already expired, because what was dropped was the reference and the object may be gone.
Decision

Expiry is availability, not erasure, and saying so is the honest version. When the last reference to an object goes, the object is deleted from the store — but a backup taken while it existed still holds it, a replica may not have caught up, and neither is something the engine can promise its way out of. An artifact that must be unrecoverable rather than merely unreachable is a workflow that should not have written it in the clear: encrypt it in the brick that produces it, hand the key to whoever collects it, and expiry then destroys the only copy that was ever readable. That is a property of the workflow, not of the platform, and the platform pretending otherwise would be the more dangerous design.

The graph and its ports

A workflow declares its own named inputs and outputs. So does every step. An edge connects one output port of a step to one input port of another. That is the only form of dependency: there is no implicit stage, and the order in which steps appear in the file has no bearing on scheduling.

Scheduling semantics

  • A step becomes runnable once every declared input port is satisfied. This is a barrier, not a continuous stream.
  • A port produces exactly one envelope, once, when the emitting step ends. A step split into shards has its shard envelopes concatenated port by port before publication.
  • An output port declared but never written by the container publishes an empty envelope. That is not an error.
  • A step whose if condition is false moves to skipped and publishes empty envelopes on all its ports. Downstream steps decide their own fate through when.
  • Cycles are rejected at validation, before registration. Looping is done by calling a sub-workflow, with a configurable maximum depth.

Merge strategies

mergeBehaviour
wait_allWaits for every upstream port, then concatenates items in edge declaration order. Default when a step has several edges into the same port.
zipPairs items by rank. Envelopes of differing lengths produce a validation failure.
joinKey join expressed as a JSON path, for example join: { on: "$.data.customer_id" }. Unmatched items leave on the unmatched port if the step declares one.
firstLifts the barrier as soon as one upstream port has produced. The other edges are abandoned and their steps cancelled if no other consumer needs them.

Fan-out

fan_outBehaviour
noneOne container receives the whole envelope. Default.
itemOne container per item, capped by max_parallel. Each shard receives a single-item envelope.
batch(n)One container per batch of n items.
matrixCartesian product of variable lists. Every combination is a shard, with its variables injected into params.

Brick contract

An image becomes a brick as soon as it honours the contract below. No Agentiik library is required: a shell script that reads one file and writes another is enough.

Decision

Multiple outputs travel as files, one per port, rather than as a port field added to every item on standard output. Standard output then stays usable for diagnostics without corrupting the result, and a brick that crashes mid-write leaves an identifiable incomplete file rather than a truncated stream. Standard output is accepted as a shorthand for the single out port.

Brick manifest

The manifest is embedded in the image at /agk/brick.yaml. It is read on first pull and cached by digest. Standard OCI annotations are required at registry publication: org.opencontainers.image.title, .description, .version, .source, .revision and .licenses.

/agk/brick.yaml
apiVersion: agentiik.dev/v1
kind: Brick

metadata:
  name: http-request
  version: 1.4.0
  summary: Issues one HTTP request per item and returns the response.

spec:
  inputs:
    in:
      schema: { $ref: "#/definitions/request" }
  outputs:
    out:
      schema: { $ref: "#/definitions/response" }
    error:
      schema: { $ref: "#/definitions/failure" }

  params:
    url:      { type: string, format: uri, required: true }
    method:   { type: string, enum: [GET, POST, PUT, PATCH, DELETE], default: GET }
    headers:  { type: object, additionalProperties: { type: string } }
    timeout:  { type: string, pattern: "^[0-9]+(ms|s|m)$", default: 30s }

  secrets:
    - name: bearer
      optional: true
      mount: /agk/secrets/bearer

  runtime:
    network: egress          # none | egress | internal
    streaming: false         # true = JSON Lines on stdin and stdout
    user: "65532:65532"
    read_only_root: true

  resources:
    cpu: "0.5"
    memory: 256Mi
    pids: 128

  # JSON Schema 2020-12
  definitions:
    request:  { type: object, required: [url], properties: { url: { type: string } } }
    response: { type: object, properties: { status: { type: integer } } }
    failure:  { type: object, properties: { status: { type: integer }, message: { type: string } } }

Workflow language

The entry point is the source of truth for what a workflow does. It is validated against a JSON Schema 2020-12 document before a push is accepted, and the commit that carries it is the version. It is not the source of truth for who may do what: access grants live in the platform, never in the file. See Identity and access control.

agentiik.yaml, at the root of finance/monthly-invoicing
apiVersion: agentiik.dev/v1
kind: Workflow

metadata:
  name: monthly-invoicing
  namespace: finance
  labels:
    domain: billing

# --- Workflow inputs and outputs -----------------------------------
inputs:
  orders:
    schema: { $ref: "./schemas/order.json" }
    required: true
  customers:
    schema: { $ref: "./schemas/customer.json" }
    default: []

outputs:
  invoices:
    from: { step: archive, port: out }
    retain: 90d
  errors:
    from: { step: invoice, port: error }

# --- Triggers -------------------------------------------------------
on:
  schedule:
    - cron: "0 6 1 * *"
      timezone: Europe/Paris
  webhook:
    - path: /invoicing
      method: POST
      auth: hmac
      map:
        orders: ${{ trigger.body.orders }}
  event:
    - type: com.example.order.approved
      filter: ${{ event.data.amount > 0 }}

# --- Published as tools ---------------------------------------------
mcp:
  name: invoicing
  tools:
    - name: create_invoice
      description: Issue one invoice for a customer.
      input:  { from: { input: orders } }
      output: { from: { output: invoices } }
      mode: sync

# --- Reuse ----------------------------------------------------------
include:
  - path: ./common-bricks.yaml            # same commit, nothing to pin
  - workflow: finance/common
    ref: v2.1.0

vars:
  currency: EUR
  dunning_days: 30

secrets:
  billing:
    provider: vault
    path: kv/data/agentiik/billing

defaults:
  timeout: 10m
  retain: 7d
  retry:
    max: 2
    on: [transient]
    backoff: { type: exponential, base: 2s, max: 60s }
  resources: { cpu: "1", memory: 512Mi }
  network: none
  runs_on: [arch=amd64]

# --- Graph ----------------------------------------------------------
steps:

  normalize:
    image: ghcr.io/acme/agk-normalize@sha256:9f2c1d...b7e0
    inputs:
      orders: ${{ workflow.inputs.orders }}
      customers: ${{ workflow.inputs.customers }}
    outputs: [ok, rejected]
    params:
      currency: ${{ vars.currency }}

  invoice:
    extends: .api-brick
    image: ghcr.io/acme/agk-invoice@sha256:1ab74e...39cc
    needs:
      - { step: normalize, port: ok, as: in }
    if: ${{ inputs.in.count > 0 }}
    strategy:
      fan_out: item
      max_parallel: 8
    secrets: [billing]
    network: egress
    egress:
      allow: ["api.billing.example.com:443"]
    retry: { max: 4, on: [transient] }
    outputs: [out, error]

  archive:
    image: ghcr.io/acme/agk-archive@sha256:44de90...c115
    needs:
      - { step: invoice,   port: out,      as: invoices }
      - { step: normalize, port: rejected, as: rejected }
    merge: wait_all
    when: [succeeded, skipped]
    cache: true
    outputs: [out]

The workflow repository

A workflow is a git repository, served by Agentiik itself. agentiik.yaml at the root is the entry point; the rest of the tree is yours to arrange. Scripts, SQL, templates, schemas, fixtures and certificates live where you would put them in any project, and every step of every run sees them.

finance/monthly-invoicing
agentiik.yaml            # the entry point, always at the root
schemas/
  order.json
  customer.json
scripts/
  normalize.py
  lib/rounding.py
sql/
  orders.sql
certs/
  internal-ca.pem
  • git push is registration. A pre-receive hook validates agentiik.yaml and either creates a version or rejects the push, so a workflow that does not validate never lands on the branch at all.
  • A version is a commit. finance/monthly-invoicing@a3f9c1e names exactly one tree, permanently, because that is what a commit already is. Nothing else has to be hashed, manifested or pinned.
  • The whole tree is mounted read-only at /agk/repo/ in every step. AGK_REPO points at it and AGK_COMMIT carries the commit.
  • A run pins the commit it started from. The branch may move a minute later; the run does not move with it, and neither does a replay of it six months on.
steps reading from the tree
  normalize:
    image: python:3.13-slim@sha256:1c4d5e...9a02
    script:
      - python /agk/repo/scripts/normalize.py
    outputs: [ok, rejected]

  load:
    image: postgres:17-alpine@sha256:8e21af...4b70
    # this repository also holds a 2 GiB fixture directory,
    # which has no business being copied to a runner for this step
    files:
      - ./sql/**
      - { from: ./certs/internal-ca.pem, to: /etc/ssl/certs/internal-ca.pem, mode: "0444" }
    script:
      - psql -f /agk/repo/sql/orders.sql
  • A step that says nothing gets the whole tree. files narrows it, and its long form relocates a path to wherever a tool insists on finding it. Narrowing is an optimisation for large repositories, never a requirement, and never a permission boundary: everything in the tree is readable by anyone who can read the workflow.
  • Trees are content-addressed and cached on the runner by commit, so a fleet fetches a given commit once and not once per task.

Branches

  • The default branch is what schedules, webhooks and events run.
  • Any other ref runs manually: agk run --ref feature/vat-rounding, which is how a change gets tried before it is merged, against real inputs, without touching what production runs.
  • Protecting the default branch is the same grant:manage permission that governs sharing. There is no second mechanism to keep in step with the first.

Git access follows the permission model

Git operationPermission required
clone, fetchworkflow:read
push to an ordinary branchworkflow:write
push to the protected default branch, force-push, delete a refgrant:manage
Decision

The repository is integrated, not connected. Agentiik hosts it rather than cloning from an external forge, and the difference is the whole point: a runner still never speaks git and never holds a credential, because the controller resolves a commit to a tree and the runner fetches content-addressed objects with the task's grant, exactly as it fetches an artifact. What hosting buys over a connection to a forge is that a version cannot drift beneath a run, an invalid workflow cannot be pushed at all, and repository access is the permission model that already exists rather than a second one to reconcile with it.

Decision

Objects are stored in the object store as packfiles and refs live in PostgreSQL. The obvious implementation, a shared POSIX filesystem across the API nodes, is what most git servers assume and is exactly what the redundant profile does not otherwise need: it would add a stateful component to a design that has carefully avoided one. Refs in the database also make a ref update an ordinary transaction beside every other piece of state.

Decision

A file in the tree is bytes, never a template. It reaches the container exactly as it was committed: no interpolation, no expression evaluation, no per-run rendering. Substitution belongs in params, which the script reads. The moment a file were rendered per run, the commit would stop describing what actually executed, and the guarantee above would quietly become false while still looking true.

A file in the tree is versioned with the workflow and readable by anyone holding workflow:read on it. An internal certificate authority belongs here; the key that matches it does not, and goes in the namespace secret store like every other secret.

agk run --local is the one run no commit describes: it executes the working tree as it stands, uncommitted changes included, and the run is labelled as such so that it is never mistaken in a history for something reproducible.

Running a script instead of a brick

Not every step deserves an image of its own. A step may carry script instead, and the commands run inside image under exactly the contract every brick honours: the same mounts, the same environment, the same isolation, the same exit-code meaning. What changes is only that the image is a base image rather than a published brick, so no manifest is read and nothing about its ports is inferred.

a step written as a script
  check-vat:
    image: alpine:3.21@sha256:5f8b1e...c704
    needs:
      - { step: normalize, port: ok, as: in }
    outputs: [out, error]
    params:
      endpoint: https://vat.example.com/v2
    # default is ["/bin/sh", "-e"]
    shell: ["/bin/sh", "-eu", "-o", "pipefail"]
    before_script:
      - apk add --no-cache jq curl
    script:
      - agk items | jq -r '.data.vat_number' > /tmp/numbers

  • Commands run as the image's user, with the shell named by shell, and the first non-zero exit ends the step with that code, which the exit-code table then interprets.
  • Input arrives where it always does: the envelope on standard input and at /agk/in/<port>/envelope.json, artifacts beside it.
  • Output is whatever the script writes to /agk/out/ports/<port>.json. A script that writes nothing and exits 0 publishes, on out, one item carrying its captured standard output and any file it left in /agk/out/files/. That is what makes a two-line script worth writing.
  • /agk/bin/agk is mounted read-only: a static helper for scripts that want to be precise rather than lucky, with agk items, agk emit and agk attach. It is a convenience, never a requirement; jq and a redirect do the same job.
  • params has no manifest to be validated against here, so each entry is written to /agk/params.json and exported as AGK_PARAM_<NAME>.
  • The image is pinned by digest in production, exactly as a brick image is. A floating base image would make a step's behaviour change without its file changing, which is the one thing the versioned workflow exists to prevent.
Decision

There is no shell executor. A step never runs commands in the runner's own shell, on the runner's own filesystem, as the runner's own account, and no configuration turns that on. GitLab, which offers one, documents the consequence in its own words: "Generally it's unsafe to run jobs with shell executors. The jobs are run with the user's permissions (gitlab-runner) and can 'steal' code from other projects that are run on this server", and elsewhere, "High-security risks exist to your runner host and network when running builds with the shell executor." In a product whose whole access model rests on namespaces, that would hand anyone holding workflow:write in any namespace code execution as the runner account on a shared host, which is every other namespace's secrets, artifacts and running containers. script gives the same ergonomics inside the container that was going to be started anyway.

Includes and inheritance

Hidden blocks and includes cover reuse without introducing a macro system or a generation loop. Resolution is ordered: includes first, in declaration order, then extends depth-first, then defaults, then the step's own values. A path include resolves inside the same commit, so it can never be stale and nothing has to pin it. A workflow include resolves another repository at a tag or a commit, requires workflow:read on it, and records the commit it resolved to in the run.

Publishing the workflow as tools

A workflow becomes callable by a model-driven client when, and only when, the entry point says so. The mcp block is where it says so: a root-level block beside inputs and outputs, declaring which of them are exposed, under what names, and with what descriptions. It is part of the language rather than a setting in the console because it belongs to the version: publishing a tool, renaming one or withdrawing one is a commit, reviewable and revertible like any other change to the file. Native MCP covers what happens on the wire; this covers what is written.

What validation refuses

These are language rules, so they are checked before the push is accepted rather than at the first call. A workflow whose published surface does not hold together cannot reach the branch.

  • An input.from or output.from naming something the workflow does not declare. The reference is to a workflow input or output, never to a step or a port: a tool is a view of the workflow's own boundary, which is what keeps the graph free to change beneath it.
  • Two tools with the same name, or a name that is not a valid identifier.
  • A tool whose input is a workflow input carrying no schema. A tool has to publish an inputSchema, so the input it maps has to have one — the surest way to discover a workflow input that was never given a schema.
  • mode: sync with a timeout above the ceiling, or timeout on an async tool, where it would mean nothing.
  • An mcp block in an included file. Reuse applies to steps and defaults; the published surface is declared by the workflow that publishes it, so that reading one file tells you everything that workflow exposes.
Decision

The tool's schema is the workflow input's schema, used as it stands, and there is no way to write a second one. A separate tool schema would be the more flexible design and the wrong one: two schemas for the same value drift, and they drift silently, because nothing fails until a client sends something the workflow rejects. Tying them together costs a little expressiveness at the boundary and removes a class of bug entirely — and where the two genuinely differ, the honest answer is a workflow input shaped for callers, not a second schema describing the first.

Expressions

Conditions and templating use CEL, the Common Expression Language. The choice rests on the guarantees in its specification: CEL "evaluates in linear time, is mutation free, and not Turing-complete", which makes evaluation terminating, free of side effects, and markedly faster than a sandboxed JavaScript engine. A workflow engine evaluates thousands of conditions per run, inside the controller process, on behalf of many tenants at once; it cannot afford a language whose evaluation a user can make diverge.

The interpolation syntax is ${{ ... }} inside a YAML string. An expression that fills the whole value keeps its type; an expression embedded in a string is converted to text.

Identity and access control

One installation serves many people. A workflow belongs to exactly one namespace, and access is granted by binding a principal to a role, either on the whole namespace or on a single workflow. Every request is authorised at the API boundary, deny by default: the API decides explicitly to permit or refuse, and no check is ever delegated to a client.

Authentication

A user authenticates with a passkey. Web Authentication Level 3 became a W3C Recommendation on 25 August 2026, and a passkey in the FIDO Alliance's terms is "a FIDO authentication credential based on FIDO standards, that allows a user to sign in to apps and websites with the same process that they use to unlock their device". A password remains available as a fallback, and an installation can remove it entirely.

The policy is set for the installation and may be tightened, never loosened, per namespace. A namespace can demand device-bound passkeys of everyone who holds a grant in it while the rest of the installation runs on synced ones.

Decision

TOTP is not stacked on top of a passkey. With user_verification: required the assertion already proves possession of the authenticator and the gesture that unlocks it, so a code from a third place adds friction and no factor. TOTP remains available, and only, where a password still exists. An installation that forbids passwords therefore has no TOTP either, and that is a simplification rather than a gap.

Synced or device-bound

The FIDO Alliance separates "passkeys that are synced between user's devices via a cloud service" from "those that never leave a single device (including those on FIDO security keys or UAF apps)". Both are recorded per credential from the Backup Eligibility and Backup State flags, and the console shows which kind each user holds, because an administrator who cannot see that cannot reason about their own exposure.

The trade is worth stating rather than resolving: a synced passkey moves the trust to the cloud account that syncs it, and a device-bound one moves it to a piece of hardware that can be lost. device_bound_only exists for the accounts where the first is unacceptable, and min_passkeys exists because the second has a failure mode that policy alone does not cover.

Turning passwords off without locking anyone out

  1. The policy moves to passkey: required while passwords are still allowed. Users enrol at their next sign-in.
  2. During the transition a password still authenticates, but the session it produces can do exactly one thing: enrol passkeys. It cannot read a workflow, start a run or mint a token.
  3. When a user holds min_passkeys credentials, their password hash is deleted. Not disabled: deleted.
  4. The policy moves to password: forbidden. Any account that has not enrolled by then is suspended rather than left reachable by a password the policy says no longer exists.

Recovery

  • The first line is min_passkeys. Two credentials on two devices is what makes a lost phone an ordinary Tuesday.
  • The second is an administrator-issued recovery code: single use, short lived, and authorising exactly one action, enrolling a new passkey. It is written to the audit log with the administrator who issued it and the account it was issued for.
  • The third is break-glass: at least one administrator account whose recovery path is documented and held offline. If every administrator loses their authenticator on the same day, no software fixes that; a sealed envelope does.
  • What is never offered is a recovery link sent by mail. It would put the account back behind a mailbox and give away the phishing resistance the passkey was adopted for.
Decision

Forbidding passwords does not touch automation. A service account holds neither a password nor a passkey, only API tokens, and the policy does not apply to it. What changes for a human at a terminal is how the token is obtained, not that one exists: agk login opens a browser, the passkey ceremony happens there against the same Relying Party, and the command line receives a token at the end of it. The mobile applications do the same through the platform's native passkey APIs. Enforcing passkeys is a change to how people prove who they are, never a change to how machines do.

Scopes and resolution

  • A grant binds one principal, one scope and one role. A scope is either a namespace or a single workflow.
  • Effective permissions are the union of every grant that applies: the principal's own grants plus those of the groups it belongs to, at namespace scope and at workflow scope.
  • A workflow-scope grant can only add to what the namespace gives. Removing something requires an explicit deny entry, which wins over any allow at any scope.
  • Nothing is implicit. A principal with no matching grant is refused, and the refusal is the same 404 whether the workflow is absent or merely invisible, so that listing cannot be used to discover names.
  • A grant may carry an expiry, after which it stops applying without anyone having to remember to revoke it.
  • Every user owns a personal namespace named after their login, created on first sign-in, which they cannot delete or rename.
Decision

Grants live in the platform database and are managed through the API and its clients. They are deliberately absent from the workflow YAML. Putting them in the file would make workflow:write equivalent to grant:manage: anyone able to edit a workflow could hand themselves ownership of it in the same commit. It also keeps the file portable, since the same YAML can be registered in two installations with entirely different populations.

Administrators

  • A platform administrator manages users, groups, namespaces, quotas, runners and runner policies.
  • An administrator does not implicitly hold run:read_data anywhere. Reading another namespace's run payloads requires granting themselves access first, which is a distinct action written to the audit log and visible to the namespace owners.
  • The first administrator is created by the installer through a one-time bootstrap token, which is invalidated on first use.

What sharing does not expose

  • Secret values, never, at any role. editor and owner see secret names and where they are mounted; the value is only ever materialised inside a container.
  • Artifacts from another namespace. A presigned URL is issued for one artifact of one run and expires in minutes.
  • Runner internals. A user never learns which host executed a task beyond its runner name and labels.
  • The existence of workflows they cannot read, in any listing, search result or error message.

  • The web console uses an opaque session identifier in a cookie marked HttpOnly, Secure and SameSite=Lax, with server-side revocation and an idle expiry. §

Runtime architecture

The controller holds the state and makes every decision; runners execute and decide nothing. No runner reaches the database or the secret store: it receives tasks over the bus and gets short-lived tokens and presigned URLs for everything else. A compromised runner therefore exposes the tasks it runs, not the installation.

From trigger to result

  1. A trigger fires. The API authenticates it, authorises it, resolves the ref to a commit, writes the run and notifies the controller.
  2. The controller evaluates the graph at that commit and finds the steps whose every declared input port is already satisfied.
  3. For each of them it creates one task per shard and publishes those tasks on the queue that matches the step's runs_on labels. It does not choose a machine, and it does not start one.
  4. A runner that is already registered, already running and already polling takes a task from that queue when it has room. Nothing was pushed to it and nobody connected to it.
  5. That runner fetches what the task names: the image by digest, the repository tree at the commit, the input envelopes and artifacts through presigned URLs, and the secret values, each of the last three obtained by redeeming the task's grant.
  6. It creates one container, runs it, waits for it to exit, collects the output envelopes, the artifacts, the log and the exit code, uploads what has to be uploaded, then destroys the container and the working directory.
  7. It publishes a result on the bus. The controller consumes it, writes the new state, evaluates the graph again and publishes whatever has just become runnable.
  8. Steps three to seven repeat until nothing is runnable, at which point the run reaches a terminal state.
Decision

The runner is not the ephemeral thing; the container is. A runner is a long-lived agent that pulls work, and the platform has no way to start one, reach one or place work on a named one. That inversion is not a detail of the implementation, it is what makes a runner in a demilitarised zone, on a bare-metal host or in a network somebody else controls a firewall rule rather than a project. It also bounds the cost of losing one: a runner holds no graph, only the tasks in its hands, so its disappearance costs those tasks and nothing else. Capacity is added by starting more agents, never by the platform reaching out.

Controller

  • Evaluates the graph on every task state change and publishes the tasks that have become ready.
  • Holds concurrency-group locks, per-step parallelism counters and per-namespace quotas.
  • Re-checks authorisation when a run is created, against the principal recorded on the trigger.
  • Emits the notification events that the API turns into push messages: failure, approval requested, completion of a run the recipient started.
  • Runs as several instances with one active at a time, elected by a session-level PostgreSQL advisory lock. Failover is a state resume, never a rebuild: the state lives in the database, not in the process.

Task bus

NATS JetStream, with WorkQueue retention, where a message is removed as soon as it has been consumed, which is precisely what work distribution needs. Consumers are durable and of the pull kind: a runner asks for a batch of tasks when it has room, which makes distribution naturally proportional to each host's real capacity without the controller having to model load.

JetStream guarantees at-least-once delivery. Every task is therefore built to be replayable: it carries an idempotency key run_id/step/attempt/shard, and the runner refuses to start a container for a key that has already completed.

A task message carries no business payload and no secret value: it names the run, the step, the image digest, the resolved parameters minus secret material, and the URIs the runner must fetch. Fetching them requires the short-lived token issued with the task, which is scoped to that run alone.

Runner

  1. Pulls a batch of tasks from its consumer, filtered by its declared labels and by the namespaces its policy accepts.
  2. Resolves and downloads the image by digest, verifying its signature where policy requires it.
  3. Downloads input artifacts into a local working directory and prepares the mounts.
  4. Creates the container (POST /containers/create), starts it (POST /containers/{id}/start), attaches to it, waits for it to exit and collects its logs, through the ContainerCreate, ContainerStart, ContainerAttach, ContainerWait, ContainerLogs and ContainerRemove calls of the Docker Engine API, whose current version is v1.56.
  5. Uploads output artifacts through presigned URLs, publishes the task result on the bus, then destroys the container and its working directory.
  6. Emits a heartbeat throughout execution. A prolonged absence moves the task to the lost state.

The runner also follows the daemon event stream (GET /events) to catch container exits it did not cause, an out-of-memory kill for instance. A runner policy can restrict a host to a list of namespaces, which is how a namespace gets dedicated capacity without a separate installation.

The agent ships as a container and as a single static binary, and the two are the same program. On a physical host it runs as a system service under an unprivileged account, which is what lets a machine chosen for its GPUs, its local NVMe or its network position join a fleet without also running a container platform for the agent itself. It opens no inbound port in either form: every connection is outbound, to the API and to the bus. See Deployment profiles.

How the API and the controller stay in step

  • They share the database and nothing else. There is no remote call between them, in either direction.
  • When the API creates a run it commits the row and issues a NOTIFY carrying the run identifier. PostgreSQL delivers such an event only once the transaction commits, and only to sessions currently listening.
  • A controller that was restarting therefore misses notifications, so it also sweeps for actionable work on a fixed interval. The notification is a latency optimisation; the sweep is the correctness guarantee.
  • A notification carries an identifier and nothing else, which keeps it far below the documented 8000-byte payload limit.
Decision

The active controller holds a session-level advisory lock, not a lease with an expiry. PostgreSQL documents that such a lock "is held until explicitly released or the session ends", so nothing has to invent a timeout or trust a clock: the lock frees itself when the process exits or when the server notices the connection is gone. Standbys call the non-blocking variant on a loop and take over the instant it succeeds. Because a partitioned former holder may not yet know it has lost, every controller write carries the lock's acquisition counter as a fencing token and a write bearing an older counter is refused. Election alone would not be safe; the fencing token is what makes it so.

Heartbeat

  • A runner posts one heartbeat every 10 seconds to the API, listing the idempotency keys it currently holds. One request covers every in-flight task on that host.
  • Liveness therefore lives in the database beside the task state, rather than as traffic on a work queue that exists to distribute work.
  • Three missed intervals move a task to lost, which is the state whose consequences Lifecycle and replay describes.
  • The heartbeat is also how a revoked credential takes effect and how the console knows a runner is present: there is no separate liveness channel to keep in sync.

Registering a runner

Registration exists to answer one question safely: how does a machine nobody has met prove which pool it belongs to, and get credentials that are worth having only on that machine.

  1. An administrator creates a runner pool with its labels, its accepted namespaces and its resource ceilings, then issues a join token. The token is single use, short lived (one hour by default), and bound both to that pool and to the exact set of labels a runner may claim with it.
  2. On the host, agk runner join --api https://agentiik.example.com --token agkjoin_…. The runner generates a keypair locally and sends the public key, the labels it claims, its capacity in vCPU, memory and disk, its architecture and its agent version. The private key never leaves the machine.
  3. The API verifies the token, checks that the claimed labels are a subset of what the token permits, refuses anything else, creates the runner record and returns a runner identifier and a long-lived credential.
  4. The credential is written to /etc/agentiik/runner.env with mode 0600, owned by the unprivileged account the agent runs as. The join token is spent and cannot be replayed.
  5. From then on the runner authenticates every call to the API with that credential, and asks the API for a short-lived bus token whenever the previous one nears expiry. Bus credentials are therefore never at rest on a runner host, which is what lets a runner sit in a zone where a stolen disk must not yield a working queue consumer.
  6. The runner announces its labels and capacity, begins heartbeating, and starts pulling from the queues its labels match.

Afterwards

  • Identity across restarts is the keypair on disk. A reimaged host is a new runner and joins again; its old record is left for the audit log rather than silently reused.
  • Rotation is automatic on a schedule. A runner offline past the rotation window must re-join, which is deliberate: a machine that has been dark for a month should be reconsidered, not readmitted.
  • Revocation from the console takes effect at the runner's next heartbeat. The runner stops accepting new tasks and drains what it holds; its results are still accepted for a grace period, so revoking a credential never destroys work already done.
  • Labels are not self-asserted. A runner can only ever claim labels its join token allowed, so a machine cannot add zone=lan to itself and start receiving the steps that were kept off the internet.

Memoisation and replay

  • With cache: true, the key is the digest of the image digest, the resolved parameters and the input envelope digests concatenated, prefixed by the namespace. A cache hit republishes the same envelopes without starting a container, and never crosses a namespace boundary.
  • Replaying a run from a step reuses the envelopes and artifacts already produced upstream; content addressing guarantees that nothing is rewritten. It also assumes they are still there: once they have expired, the run can be replayed only from the beginning, and a cache entry pointing at an expired artifact is not a hit.   • A step declared idempotent: false is excluded from the cache and from requeue after loss. The default is true, which puts the burden on the brick author.

Decision

workflow:write is arbitrary code execution, and saying so plainly is part of the design. A workflow names container images and shell commands, so anyone able to push to a workflow repository can run code of their choosing inside a container on a runner in that namespace's pools. That is not a weakness awaiting a fix, it is what the product does. The consequence is the sentence that should govern how the grant is handed out: workflow:write is a trust decision of the same weight as commit access to a running service, and the container plus the runner pool is the boundary that contains it. A namespace whose authors are not trusted to that degree gets a pool of its own, and a sandboxed runtime on it.

Three tiers of containment

Supply chain

  • Images are referenced by digest in production. A tag is a mutable pointer and has no place in something that claims a commit determines what ran.
  • Signature verification is a per-namespace policy naming which identities may sign, enforced by the runner before the container is created rather than by the registry it pulled from.
  • The standard catalog targets SLSA Build Level 3, which asks that a build platform "implements strong controls to prevent runs from influencing one another" and "prevent secret material from being accessible to user-defined build steps". Those are the same two properties this specification demands of a run, which makes building the catalog on Agentiik itself a reasonable ambition and not a circular one.
  • Each catalog image publishes an SBOM as an OCI referrer, so that an operator answering "are we affected" reads an attestation rather than unpacking a filesystem.
  • Catalog images are rebuilt on a schedule and on base-image advisories, and the catalog shows the age of each image, because an image that has not been rebuilt is not stable, it is stale.

Secrets, honestly

Decision

A secret handed to a step can be exfiltrated by that step, and no amount of secret-store engineering changes it: a brick that legitimately receives an API key can also send it somewhere else. The only control that actually bites is egress, which is why egress is per-step and default-deny rather than per-runner. network: none is the default, egress.allow names hosts and ports, and a proxy on the runner enforces the list. Everything else about secret handling, the tmpfs mount, the last-moment retrieval, the masking, reduces incidental exposure. None of it constrains code the workflow author deliberately chose to run.

  • Masking is a literal match against the values the task was given. It catches a secret printed as it arrived, and does not catch one that was base64-encoded, URL-encoded, split across lines or hashed first. It is a guard against accident, never against intent.
  • The built-in store uses envelope encryption: per-secret data keys wrapped by a master key held outside the database, so a database dump alone yields nothing.
  • Rotation is a write. No role reads a secret value back through the API, so rotating is replacing rather than reading and replacing.
  • Revoking a grant does not retroactively protect a secret a step already used. Rotation does. The console says so at the moment of revocation rather than leaving the operator to reason it out.

Webhooks

  • HMAC-SHA256 over the raw body with a per-trigger secret, compared in constant time. The raw body, not the parsed one, because two JSON encoders do not agree on whitespace.
  • A timestamp inside the signed material, a rejection window of five minutes, and a nonce cache covering that window, so a captured request cannot be replayed inside it or outside it.
  • Signature failures are counted per trigger and surfaced, not merely refused. A webhook whose signatures suddenly fail is either a rotated secret nobody announced or somebody guessing.

Two questions that come up

  • The image cache is shared between namespaces, and that is fine. A runner caches layers by digest. A digest is not a secret, so the control is not cache separation but entitlement: the runner checks that the requesting namespace may use the reference before it starts anything, and private registry credentials are namespace secrets, so no namespace can cause a pull it is not entitled to. A cached layer discloses nothing that knowing the digest would not.
  • The audit log is append-only and chained. Each entry carries the hash of the one before it, so a deletion or an edit leaves a break rather than a silence. It is exported continuously to a store outside the installation, because an audit trail that lives only where the incident happened is evidence you may not get to read.

What this does not defend against

  • A compromised control-plane node. It holds the database credential and the secret-store role, so it can obtain whatever the secret store would give it. Nothing in this design pretends otherwise. What reduces the damage is scoping the secret-store role to the namespaces the installation actually uses, and rotating on suspicion rather than on schedule.
  • A malicious administrator. Constrained and recorded, not prevented. The audit chain makes the actions visible afterwards; it does not stop them.
  • A brick that mishandles its own input. A brick that logs what it was given has logged what it was given. The catalog is reviewed; a third-party brick is the author's responsibility.
  • Container escape through a kernel vulnerability. That is what the sandboxed tier and a separate pool exist for, and why the choice between tiers is a real decision rather than a default.
  • Traffic analysis. Somebody who can watch the network learns when runs happen and roughly how large they are.

Disclosure

  • A security policy in agentiik/.github, shared by every repository, naming a contact and a coordinated disclosure window.
  • Advisories published against the affected repository, with an identifier assigned where one is warranted, and the fixed versions named per component rather than for the project as a whole, because the components release independently.
  • The SBOM published with each catalog image is what lets an operator answer an advisory about a dependency without waiting for one about Agentiik.

Further rules

  • The daemon socket is never mounted inside a brick. A brick that needs to build an image goes through an unprivileged builder, run like any other brick.
  • The container user is non-root, required by the manifest and checked at publication.
  • Images are referenced by digest in production. Signature verification is a registry policy, enforced by the runner before start.
  • The working directory of a task is created fresh, owned by an unprivileged account, and removed with the container, so no residue of one namespace survives into the next task on that host.

Secrets

  • A secret belongs to a namespace. A workflow can only reference secrets from the namespace that owns it, so moving a workflow elsewhere breaks unresolved references at validation rather than silently carrying access along.
  • A secret is mounted on tmpfs at /agk/secrets/<name>, never injected as an environment variable by default, because a process environment is readable by its children and ends up in diagnostic dumps.
  • The runner obtains the value at the last moment, through a short-lived token issued by the controller for that one task and that one secret.
  • Secret values are masked in collected logs by literal match against the values known to the task, before anything is written to the store.
  • A secret is never reachable from condition expressions, only from params marked sensitive in the brick manifest.
  • No role reads a secret value through the API. Rotation is a write, never a read-then-write.
  • Supported providers: built-in encrypted store, HashiCorp Vault, and controller environment variables for development use.

Native MCP

Agentiik speaks the Model Context Protocol on two surfaces, and they answer two different questions. One lets a client operate the platform: list workflows, author one, commit to it, run it, read the result. The other lets a single workflow present itself as a tool, so that calling it is indistinguishable from calling any other MCP server. Both are servers. Neither contains a model.

Decision

MCP puts no model in the engine. Agentiik is the server: it publishes tools and answers calls. Whatever model is involved lives in the client, on the far side of a protocol boundary the engine never crosses. The rule stated in Scope holds unchanged, with no exception carved for this chapter: no language-model node and no agent, in the engine or in the standard catalog. What MCP adds is one more kind of caller, subject to exactly the permissions every other caller already obeys.

Protocol

  • Revision 2026-07-28. Every request declares its version in _meta under io.modelcontextprotocol/protocolVersion, and on HTTP in the MCP-Protocol-Version header. server/discover is implemented because the specification requires servers to implement it.
  • Transport is Streamable HTTP on a single endpoint accepting POST and GET, with the Origin header validated on every connection as the transport requires, and an Mcp-Session-Id issued at initialisation.
  • Authorisation is OAuth 2.1, with Agentiik acting as a resource server: it publishes Protected Resource Metadata, validates that a token was issued for it as the audience, answers 401 for an invalid token, and 403 with WWW-Authenticate: Bearer error="insufficient_scope" when a scope is missing. It never accepts or forwards a token issued for anything else.
  • An ordinary API bearer token is also accepted, which is how a service account drives the platform without a browser in the loop.
  • The instructions field of the discovery response carries the orientation a client needs before its first call: that a workflow is a git repository, that the entry point is agentiik.yaml at its root, that workflow.language comes before drafting and workflow.validate before committing. The specification describes that field as "natural-language guidance for LLMs on how to use this server effectively", which is exactly what it is used for and nothing more.

Decision

The tool list is filtered by the caller's permissions, and a tool the caller cannot use is absent rather than refused. The protocol allows this explicitly: the tool set "MAY vary by the authorization presented on the request — for example, returning only the tools the caller's granted scopes permit — since credentials are per-request input, not connection state". A principal who can write in no namespace therefore never sees workflow.commit, which is both a smaller attack surface and a smaller context window.

Decision

A client authors by committing. workflow.commit produces a real git commit, attributed to the calling principal and marked as having arrived through MCP, so git log and the audit log tell the same story. There is no side channel that changes a workflow without leaving a commit behind, and workflow.validate exists so that a client can iterate without landing broken ones. The pre-receive hook remains the backstop for the ones it tries anyway.

Teaching a client the language

A client that is going to write a workflow needs three different things, and they are three different mechanisms rather than one large one.

What it needsWhere it comes from
What the language isworkflow.language, one topic at a time, example first. Also published as resources at agentiik://language/{topic} for clients that prefer to attach documents.
What is legalworkflow.schema, the JSON Schema document itself, for local validation or type generation.
Whether this draft is legalworkflow.validate, which is the only authority. Nothing else decides.

workflow.language takes an optional topic and returns a page, not a manual: a summary, the keywords that belong to it, the fragment of schema that governs them, and worked examples. With no topic it returns an orientation, a complete minimal workflow, and the list of topics. The topics are the sections of the language itself: repository, inputs, outputs, triggers, steps, ports, needs, merge, fan_out, retry, expressions, secrets, files, script, includes, mcp.

Decision

The language documentation is generated from the schema, never written beside it. Every keyword's prose and every example in workflow.language is a projection of the description and examples fields of the JSON Schema in agentiik/schemas, and the build fails if a keyword exists without them. Two hand-maintained sources would eventually disagree, and the failure mode is the worst available: a tool confidently teaching a model syntax that the pre-receive hook then rejects, over and over, because the model has no reason to doubt what it was told.

Decision

A validation error is written for the reader that will act on it. Each one carries a JSON Pointer to the offending node, what was expected there, and the name of the workflow.language topic that covers it. That closes the loop: an error does not merely say no, it says which page to read. The same errors are what the command line prints and what the console shows, so no audience gets a worse explanation than another.

The intended sequence is therefore: workflow.language to learn the shape, brick.list and brick.get to find the bricks and their parameter schemas, a draft, workflow.validate until it passes, then workflow.commit. Only the last step has a side effect, and the three read-only tools carry readOnlyHint so a client can tell without being told.

        from: { input: period }
      mode: async
  • inputSchema is the workflow input's own JSON Schema, used as it stands. There is no second schema to write and therefore no way for the two to drift apart.
  • outputSchema is the output's schema when it declares one. The result carries that output's envelope in structuredContent, with a text rendering alongside it for clients that want one.
  • mode: sync waits for the run and returns the output, under a ceiling of 120 seconds because clients time out. A workflow that cannot finish inside it must be async, which returns the run identifier at once.
  • Following an asynchronous run is the platform server's run.get. A workflow's own server never grows a polling tool of its own.
  • A tool call is a run. It is attributed to the calling principal, carries trigger_kind: mcp, appears in the run list beside every other run, and obeys the namespace quota and the workflow's concurrency group. A client calling in a loop meets the same rate limit a webhook would.
  • Listing and calling both require workflow:run. Neither requires workflow:read.
Decision

The MCP surface is declared, never inferred. Nothing about a tool is derived from the graph: not its name, not its description, not its schemas. Inference would make exposing a workflow leak its internals to everyone allowed to call it, and would tie a published interface to an internal refactor. Because the surface is declared, operator — the role that deliberately carries no workflow:read — turns out to be exactly the right grant for a client: it can list and call the tools, and it cannot read the entry point, the steps, or the endpoints they talk to.

Decision

A workflow's server exposes tools and nothing else: no resources, no prompts, no access to its tree. A resource would turn workflow:run into a read path into the repository and quietly undo the separation the roles were built around.

Errors and obligations

  • A run that fails returns a tool execution error, isError: true, naming the failing step, its exit code and its message, because the specification says clients should hand those to the model so it can correct itself. A malformed argument is a protocol error instead: the input schema is what rejects it, before any run exists.
  • Secrets never appear in a result. The masking that applies to logs applies here unchanged.
What the protocol requires of a serverHow it is met
Validate all tool inputsThe workflow input's JSON Schema, evaluated before a run is created.
Implement proper access controlsThe existing permission model. An unauthorised tool is absent from the listing rather than refused on call.

Terraform provider

An installation is not only its workflows. It is namespaces, quotas, the pools each namespace may reach, groups, service accounts, and the grants that bind principals to scopes — and every one of those is the kind of thing that is set up once by hand, adjusted twice under pressure, and reproduced from memory when a second environment is needed. The provider exists so that this half is written down and applied, rather than clicked and remembered.

It is a client of /api/v1 and holds no authority of its own: a plan applies as the presenting principal and is refused by the same grants that refuse the console. Nothing is possible through Terraform that is not possible through the API.

What the provider does not manage

The boundary is not an omission and it is not a roadmap item. Two things stay out, each for its own reason; a third — starting a run — is in, but only in a shape that keeps an apply idempotent, and Running a workflow sets out which.

  • The contents of a workflow. A workflow is a git repository and agentiik.yaml is its source of truth; putting the graph in HCL would create a second one, and the two would disagree the first time somebody pushed. The provider creates the repository and stops at its first commit. What goes in it arrives by git push, validated by the same hook as every other push.
  • Secret values. The provider writes the declaration — which provider, which path — and never the value, because a value passing through Terraform is a value in the state file. The state is not a secret store, and treating it as one is the single most common way secrets escape in infrastructure code.

State, drift and authentication

  • Authentication is an API token in AGENTIIK_TOKEN, belonging to a service account with exactly the grants the configuration touches. The provider refuses a token passed as a plain attribute in a file that is, by construction, committed.
  • agentiik_api_token returns a clear value once, and that value lands in the state. It is marked sensitive, which hides it from output and not from the state file. A configuration creating tokens needs an encrypted backend, and the documentation says so where the resource is described rather than in a note somewhere else.
  • Every resource can be imported, because the first real use of the provider is always an installation that already exists. Import is by the identifier the API uses: finance for a namespace, finance/monthly-invoicing for a workflow, the grant identifier for a grant.
  • Drift is read back on refresh. A grant added in the console shows as a change to revert, which is the behaviour to want: if access is managed here, access granted elsewhere is drift, and the plan is where it surfaces.
  • The provider tracks the API version, not the core's. It declares the /api/v1 it speaks and refuses an endpoint answering a version it does not, rather than failing halfway through an apply.

Running a workflow

Starting a run is an effect, and an effect sits badly in a tool whose whole contract is that applying twice changes nothing the second time. The resolution is not to smuggle the effect in, but to declare a state that happens to require one: agentiik_run does not mean run this workflow, it means a run of this workflow, at this version, with these inputs, has happened. Applying against a configuration whose answer is already yes does nothing, which is the property that was at risk.

a migration that runs once per schema version
resource "agentiik_run" "migrate" {
  workflow = agentiik_workflow.invoicing.id
  ref      = "v2.1.0"
  inputs = {
    period = "2026-09"
  }

  wait = "15m"          # apply fails if the run fails; false returns on acceptance

  # anything here joins the identity: change it and a new run happens
  triggers = {
    schema_version = var.schema_version
  }
}

output "invoice_count" {
  value = agentiik_run.migrate.outputs["invoices"].count
}
  • Identity is the workflow, the commit, the inputs and the triggers. Change any of them and the resource is replaced, which is a new run; change none and no run happens, however many times the plan is applied. A moving ref is resolved to a commit at plan time and the commit is what enters the identity, so a branch that has advanced shows as a planned change rather than as a silent re-run — and a plan that shows nothing means nothing will happen.
  • Waiting is a choice with a consequence. wait holds the apply until the run settles, and a failed run fails the apply, naming the step, its exit code and what was refused, in that order. wait = false returns as soon as the run is accepted, and leaves the outputs empty: a configuration that reads them has to wait for them.
  • Outputs are digests; contents are a data source. The resource exports the run identifier, its state, its timings and one envelope digest per output. Reading what an envelope contains is agentiik_run_output, which requires run:read_data and is marked sensitive, because an output read into state is an output written to the state file.
  • Destroying does not undo. A run that happened cannot be made not to have happened, so terraform destroy forgets the resource and touches nothing on the server. The exception is a run still going when the resource is destroyed: on_destroy = "cancel" cancels it, and the default leaves it to finish, because cancelling somebody's half-done work on the way out of a destroy is the more surprising behaviour of the two.
  • It is a run like any other. Attributed to the token's principal, carrying trigger_kind: terraform, listed beside every other run, and subject to the namespace quota and the workflow's concurrency group. It needs workflow:run and nothing more — operator is the grant, and the provider never needs to read the file it runs.

Invoking one without declaring it

Some runs are genuinely imperative — reindex after this deploy, replay this migration now — and wrapping them in a resource means inventing a state that nobody wanted. Terraform 1.14 added actions for exactly this, and the provider exposes one:

Terraform 1.14 and later
action "agentiik_run" "reindex" {
  config {
    workflow = agentiik_workflow.search.id
    ref      = "v3.0.0"
    inputs   = { full = true }
  }
}

resource "agentiik_workflow" "search" {
  namespace = agentiik_namespace.platform.name
  name      = "search-index"

  lifecycle {
    action_trigger {
      events  = [after_create, after_update]
      actions = [action.agentiik_run.reindex]
    }
  }
}

The same action is invocable on its own with terraform apply -invoke=action.agentiik_run.reindex, which is the closest thing to agk run that stays inside the tool and its credentials.

Decision

The action is the addition, never the replacement. OpenTofu has no action block — the request is open and undecided — so a configuration built on actions runs on one of the two tools and not the other, which is precisely what the provider set out not to require of anyone. agentiik_run therefore covers every case on both, and the action exists for the one case it covers better, on the tool that has it. If OpenTofu adopts actions the two paths converge; if it does not, nothing in this documentation has to be taken back.

Decision

Neither path turns Terraform into a scheduler. A run that should happen every month is a schedule trigger in the entry point, where it is visible to everyone who reads the workflow, survives the loss of a state file, and does not depend on somebody's pipeline running apply. The provider starts runs that belong to a change — a migration for a version, a reindex after a deploy — and a run that belongs to the calendar instead belongs to the workflow.

Decision

The provider is built against the plugin protocol and is published to the Terraform registry and to the OpenTofu one, and the reason is the same reason the licensing section rejects the Business Source License. Terraform itself moved to the BUSL in 2023 and is no longer open source; OpenTofu is the fork that stayed. A project that declined to ship source-available software cannot then require its users to run some, so the provider is written to the protocol rather than to one implementation of it, carries the same Apache-2.0 as the rest of the deployment tooling, and is tested against both. Which of the two an operator runs is their decision and costs them nothing here.

Design system

The web console, the two mobile applications and the public site share one set of tokens. The system is deliberately small: one accent, one separate state ramp, two typefaces, one spacing unit. Anything a client needs beyond it is a gap in the system, not a licence to invent a value.

Colour rules

  • The accent is the only brand colour. It marks what is interactive: primary buttons, links, selection, the active rail marker, port dots on the graph.
  • The state ramp is separate from the accent, with one deliberate exception: running uses the accent hue because running is the live state. Hue is shared, form never is. A button is a solid fill with ink on it; a state is an outlined pill with a dot.
  • No state is signalled by colour alone. Every state carries a dot and a word, and a step strip carries position and width as well.
  • Elevation comes from ground value plus a hairline, never from a shadow. The four surface tokens are the whole vocabulary: sunken for code and payload panes, bg for the page, surface for panels and rails, raised for rows, controls and the active item.

Deployment profiles

The API, the controller, the console and the runner are the same images in every profile. What changes between a single machine and a redundant installation is where those images sit and what backs the four dependencies: a database, a bus, an object store and a secret store. Nothing in the workflow language, the brick contract or the access model varies by profile, so a workflow written against a laptop runs unchanged against a redundant fleet.

What every profile must provide

  • Exactly one writable PostgreSQL. The controller's leader election is a session-level PostgreSQL advisory lock, so a second writable primary does not add availability, it breaks the election.
  • A work queue with at-least-once delivery and one separate queue or subject per runner pool.
  • An object store reachable from every runner, because artifacts move by presigned URL and never travel through the controller.
  • A secret store the controller can read and the runners cannot.
  • An OCI registry every runner can pull from by digest.
  • Nothing else. Workflow repositories need no shared filesystem: their objects sit in the object store and their refs in the database, both of which are already on the list.
  • TLS terminated in front of the API, with the console served from the same origin.
  • One Relying Party Identifier, chosen at installation and never changed. The specification requires it to be the origin's effective domain or a registrable domain suffix of it, and requires that origin to be HTTPS, so the console and the API must sit under one registrable domain: a console on a content delivery network and an API behind a load balancer are fine, on two subdomains of the same name. Changing it later invalidates every passkey in the installation, which is why the installer treats it as immutable and offers a re-enrolment flow instead.

  • The built-in secret store is used, with its master key read from a file the API user alone can open, or from the host keyring.
  • Backup is a nightly pg_dump plus an object-store sync to a second disk or a NAS. Restoring both together restores the installation; restoring only one leaves runs pointing at artifacts that no longer exist.
  • The whole installation stops together during an upgrade. That is acceptable here and is stated rather than engineered around.

Profile B: on-premise, redundant

Three failure domains, which in practice means three racks, three rooms or three sites with a low-latency link. Every stateful dependency is replicated across them and every stateless one runs in all three. Runners sit outside those domains entirely, in pools selected by label, because they hold no state worth protecting.

What happens when something fails

What failsWhat the installation does
a runnerIts in-flight tasks stop heartbeating and move to lost. Each is requeued if its step is idempotent, and surfaced for a human otherwise.
the active controllerIts session ends, PostgreSQL releases the advisory lock, another node takes it and resumes from the database. Tasks already published are untouched: they are sitting in the bus, not in the process.
an API nodeThe load balancer stops routing to it. Open log streams reconnect against another node and resume from their last position.
the PostgreSQL primaryThe synchronous standby is promoted. The controller loses its advisory lock with the old primary and reacquires it against the new one, which is the same code path as a controller restart.
one NATS nodeR3 streams keep a majority and keep serving. Nothing is noticed.
two NATS nodesThe bus loses quorum. No task is dispatched and none is lost; runs stay queued until a majority returns.
one object-store nodeReads and writes continue inside the parity budget of the erasure set.
a whole domainThe two remaining domains hold a majority for the bus and for the database, so the installation keeps running with reduced headroom.
Decision

The controller is active with standbys rather than several controllers sharding the graph. Sharding would buy throughput the product does not need at this size and would cost the one property worth protecting: a single place where the graph is evaluated, so that two instances can never publish the same task from two different views of the same run.

Profile C: AWS with managed resources

The same components, with every stateful dependency handed to a managed service and only the runners left as instances someone owns. Two AWS constraints shape the profile and are worth stating before the picture.

Decision

The bus becomes SQS rather than a self-managed NATS cluster, because the bus contract is narrow enough to substitute. Standard queues state that they "ensure at-least-once message delivery", a message leaves the queue when the consumer deletes it, and a long-poll receive is exactly the pull consumer the runner already implements. What is given up is server-side subject filtering, which is why each runner pool gets its own queue, and stream replay, which WorkQueue retention never offered anyway. Task messages carry no payload and sit far below the 1 MiB message limit.

Decision

Runners are EC2 instances, not Fargate tasks. A runner drives a Docker daemon through its socket, and an ECS task definition can only bind-mount a host path where sourcePath is available, which AWS documents as "supported only when using tasks that are hosted on Amazon EC2 instances or Amazon ECS Managed Instances". The control plane, which mounts nothing, stays on Fargate.

  • The controller's advisory lock works unchanged against RDS Multi-AZ: a failover to the standby in another Availability Zone ends the session that held it, and the controller reacquires it exactly as it would after a restart.
  • Presigned S3 URLs are already the artifact path, so nothing changes in the runner: the object store simply stops being something anyone runs.
  • Egress per pool is a security group plus a NAT with a filtered allow list, which is where the egress.allow entries of a step are enforced.
  • The Auto Scaling group tracks its queue's visible-message count, so a fan-out of ten thousand items adds instances and the tail of the run gives them back.

Installing a runner

A runner is deliberately installable two ways, because the machines worth adding to a fleet are not always machines anyone wants to run a container platform on.

Registration

  1. An administrator issues a join token, single use and short lived, scoped to a pool and to a set of labels the runner may claim.
  2. agk runner join --api https://agentiik.example.com --token <token> exchanges it for a long-lived runner credential written to /etc/agentiik/runner.env with mode 0600.
  3. The runner announces its labels, its capacity and its accepted namespaces, and starts pulling from the queues its labels match.
  4. Revoking the credential from the console stops the runner at its next poll. No inbound port is ever opened on a runner host: every connection is outbound to the API and the bus.

Runner-side hooks

The machine's owner, and only the machine's owner, can have the runner run commands on the host around each task. These live in /etc/agentiik/runner.toml, readable by the agent account alone. No workflow can set them, read them, or discover that they exist.

/etc/agentiik/runner.toml
[hooks]
timeout = "30s"

# before the container is created, after the image is resolved
pre_task = [
  "/usr/local/sbin/attach-licence --slot $AGK_TASK_ID",
  "nvidia-smi -L > /dev/null",
]

# after the container is destroyed, whatever the verdict
post_task = [
  "/usr/local/sbin/release-licence --slot $AGK_TASK_ID",
  "find $AGK_WORKDIR -mindepth 1 -delete",
]
  • They receive AGK_TASK_ID, AGK_NAMESPACE, AGK_WORKFLOW, AGK_STEP, AGK_IMAGE and AGK_WORKDIR, and nothing else. Never a secret, never an envelope, never a parameter.
  • A non-zero exit from pre_task fails the task as an infrastructure failure, charged to the runner and not to the brick, and the runner marks itself unhealthy after a few consecutive failures rather than dragging a whole pool down one task at a time.
  • The task's own deadline starts once pre_task has succeeded, so a slow hook eats the runner's time and never the step's.
  • post_task runs whatever the verdict, which is what makes it the right place to release a licence seat or wipe a scratch directory.
Decision

Runner hooks and step scripts never share a shell. In GitLab a pre_build_script "Runs in the same shell context as before_script, script, and post_build_script", which is convenient and is precisely the coupling that lets a job read what the administrator's hook set up, and the reverse. Here the hook runs on the host and the script runs in a container that is created afterwards: they share the workspace directory the runner chooses to mount, and nothing else. What the workflow author gets from a hook is a machine that is ready, never a variable.

Sizing

  • Runner concurrency starts at one concurrent task per vCPU and is raised until memory or disk queue becomes the limit, not CPU. A runner refuses a task whose declared resources would take it past its own declared capacity, so oversubscription is a configuration choice rather than an accident.
  • The control plane is small and stays small: it holds no payloads, only state. It is sized by run creation rate and by the number of open log streams, never by the volume of data moving through the workflows.
  • The database is sized by run and task history, which is bounded by retention. The object store is sized by artifacts, which is not, and is what a retention policy actually controls.

First run

  1. The installer prints a one-time bootstrap token, valid for a single use and a short window.
  2. That token creates the first administrator, after which it is invalidated.
  3. The administrator creates namespaces, groups and users; every user gets a personal namespace on first sign-in.

Push notification delivery

An installation that wants mobile alerts supplies its own APNs key and Firebase service account to the API. Neither is required to run the platform, and an installation without them simply has no push, with the applications falling back to foreground polling.

One licence across an organisation is the tidy answer and the wrong one. What a repository is for decides what its licence has to allow, and these repositories are for two different things: one of them is a server somebody might host, the rest are things other people must embed in their own work.

No OSI-approved licence gives both, so the split above is a choice about which of the two the project would rather give up, and it is the one decision here that should be made deliberately rather than inherited.

Decision

A brick is not a derivative work of the engine, and agentiik/.github/LICENSING.md says so in as many words. The two exchange a JSON envelope on standard input and output, files under /agk/in and /agk/out, and an exit code, across a process and a container boundary, with no shared address space and no linking of any kind. The Free Software Foundation's own guidance is that "pipes, sockets and command-line arguments are communication mechanisms normally used between two separate programs. So when they are used for communication, the modules normally are separate programs." Stating this up front removes the one objection that would otherwise keep AGPL out of the conversation, and it costs nothing because it is simply what the brick contract already is.

Contributions

  • Contributions are accepted under the Developer Certificate of Origin 1.1, with a Signed-off-by line, not under a contributor licence agreement. The DCO is an attestation of provenance: the contributor certifies the work is theirs to submit under the project's licence. It is not a grant of rights to the maintainer.
  • That choice is deliberate and it has a cost worth naming: without a CLA, nobody can relicense the project later, because every contributor keeps the copyright in their own patch. A project that intends to sell a differently licensed edition one day needs a CLA from its first commit, and cannot bolt one on afterwards without tracking down every contributor.
  • AGPL-3.0-or-later rather than -only for the same reason: with no CLA, the "or later" clause is the one migration path a maintainer keeps.

Trademark

  • A licence governs copyright, not the name. Apache-2.0 says outright that it "does not grant permission to use the trade names, trademarks, service marks, or product names of the Licensor", and the AGPL grants none either.
  • So the right to fork the code and the right to call the fork Agentiik are separate questions, and the second is answered by a short trademark policy in agentiik/.github: the name and the mark stay with the project, a fork may say it is derived from Agentiik and may not present itself as Agentiik.

Versioning

Semantic Versioning 2.0.0, one stream per repository, released as a git tag vMAJOR.MINOR.PATCH. The components release independently, so there is no project version and nothing is tagged in lockstep: agentiik at 2.4.0 alongside console at 1.9.3 is the normal state, not a drift to be corrected.

A version number is a claim about compatibility, and a claim is worthless until it says what it covers. So each repository names its public interface, and the rules below apply to that and to nothing else. What is not on this list may change in a patch.

agentiik/bricksEach brick's ports, parameters and exit codes. One version per brick, not one for the catalog.

Before and after 1.0.0

  • 0.y.z promises nothing. Anything may change in any release, and a workflow file, a brick or a deployment may have to be adjusted to follow. This is where every repository starts, and staying there while the design is still moving is more honest than a 1.0.0 that has to be taken back.
  • 1.0.0 is the moment somebody else's work can depend on this one. It is not a statement about how finished the software feels; it is the point at which breaking the interface becomes a major version rather than an ordinary release.
  • Afterwards: a patch fixes behaviour that was already wrong, a minor adds without taking away, and a major is the only place something published disappears or changes meaning. A major carries a migration note in agentiik/deploy saying what to change and in what order, and the note ships with the release, not after it.

Pre-releases

A pre-release is a version with a hyphenated identifier — 1.0.0-alpha.3, 1.0.0-beta.1, 1.0.0-rc.2 — and it names the version it is heading towards rather than the one behind it. The three channels differ in what may still change, which is the only thing a reader needs from the label.

ChannelWhat it promisesWho it is for
alphaNothing. The interface may change between two alphas with no notice and no migration. Data written by one alpha may not be readable by the next.The people building it, and anyone willing to rebuild their setup.
betaThe interface is complete and no longer expected to change; what remains is to find out where it is wrong. Migrations are provided from the previous beta, and bugs are expected.Anyone able to run it beside their real installation rather than as it.
rcThis is the release, unless something blocking is found. Only a fix for such a finding goes in; anything else waits for the next minor. An rc that survives a week with nothing blocking becomes the release, unchanged but for its tag.Anyone who will run the release, verifying it before it is one.
  • Precedence is Semantic Versioning's own: 1.0.0-alpha.3 < 1.0.0-beta.1 < 1.0.0-rc.1 < 1.0.0, and every one of them is below 1.0.0 itself. A tool resolving a range takes none of them unless asked, which is the behaviour to rely on rather than a separate channel to publish to.
  • Counters start at 1 and never reset within a target: after 1.0.0-beta.4 comes 1.0.0-rc.1, and if the release slips to 1.1.0 the pre-releases are renumbered from 1.1.0-alpha.1 rather than continued.
  • Images carry the same string: ghcr.io/agentiik/api:1.0.0-rc.2 exists and is signed like any other. latest never points at a pre-release, and a pre-release never moves a 1 or 1.0 rolling tag.
  • A pre-release of agentiik/schemas is the one that matters most, because everything else pins it: a workflow file accepted by 2.0.0-beta.1 may be rejected by 2.0.0, and a repository should pin an exact pre-release rather than a range.
Decision

The milestones in the roadmap are not these versions, and the collision of notation is worth naming rather than leaving to be discovered. v0.4 there is a point in an order — what has to be true before what — and belongs to the project as a whole; a version here belongs to one repository and is a promise to whoever depends on it. They meet once: the roadmap's v1.0 is the milestone at which the repositories that are the service are expected to tag their own 1.0.0, because that milestone is precisely the point where somebody else can rely on them. Before then, every repository sits in 0.y.z and promises nothing, which is the accurate description of where the project is.

Conventions across repositories

  • Default branch main, releases as tags, semantic versioning per repository. Versioning sets out what each version is a promise about, and what alpha, beta and rc each mean.
  • Every repository carries the same security policy and the same code of conduct, sourced from agentiik/.github. The licence file is the one thing that is not uniform, for the reasons below.
  • The core, the console and the two applications release independently. Compatibility is expressed by the API version alone, which is why the URL carries /api/v1.
  • agentiik/schemas is the only cross-repository dependency for the workflow format. Nothing else redefines those shapes, and a schema change is a release of that repository first.
  • Images are published to ghcr.io/agentiik/<name>, signed, and carry the same OCI annotations required of any brick.
  • Documentation lives in agentiik/agentiik.github.io, not scattered in each repository, so that a reader never has to guess which copy is current. Each repository keeps only a short README pointing there.
  • All documentation and code, including comments, identifiers and commit messages, are written in English.

Out of scope for v1

  • External identity providers. v1 has local accounts only, authenticated by passkey; OIDC federation and SCIM provisioning are deferred, and the principal model is kept provider-agnostic so that adding them later touches authentication and not authorisation.
  • An external policy engine. Roles and grants are evaluated in the API against the database; delegating to OPA or Cedar is deferred.
  • Field-level permissions inside an envelope. Sensitivity is handled at the port and at the run, not per attribute.
  • Workflow authoring on mobile, and any offline editing.
  • Kubernetes as a substrate. The container driver sits behind an Executor interface so that adding a Job or Pod executor touches neither the controller nor the language.
  • Hardware-level tenant separation. Namespaces are an authorisation and quota boundary on a shared fleet; a namespace that requires physical separation gets a dedicated runner pool rather than a separate isolation model.
  • Long-running bricks and continuous streams. The contract rests on a per-port barrier; a streaming mode over JSON Lines exists at brick level but stays bounded by the task duration.
  • Loops in the graph. Only sub-workflow calls, with a maximum depth, are allowed.
  • A public brick marketplace. The registry stays an OCI registry, and discovery is limited to one installation's catalog.
